The Reality of AI Coding

The "Agent Drift" Crisis

LLMs don't fail because they can't write code. They fail on multi-turn tasks because free-hand document editing leads to silent drift, hallucinated completion, and prompt bloat.

✕

Without Stepwell

  • •
    Corrupted Documentation: The agent manually modifies Markdown tables, destroys pipes, forgets headers, or deletes previous context.
  • •
    Token Waste: Agent re-reads entire 2,000-line progress files on every session turn, burning 30,000+ context tokens unnecessarily.
  • •
    Hallucinated Progress: Checked-off items linger in open lists; completed steps have no verifiable commit SHA audit trail.
  • •
    Scope Creep: Agent takes on 4 tasks at once without approval gates, breaking tests in unrelated directories.
✔

With Stepwell

  • •
    Deterministic Tool Mutations: The agent never touches table formatting directly. 14 tools cover reads, mutations, and repairs (`progress_update`, `archive_item`, `backlog_add/update/remove`, `docs_repair`) — every write dry-run first.
  • •
    Radical Token Economy: `docs_status` with `nextStepScope` gives the exact target in 1 call. SHA-256 hashes short-circuit redundant reads; `fields[]` projection keeps payloads lean.
  • •
    Dry-Run First & Audit Trails: Every write yields a line-diff preview and is re-parsed and verified after apply. Completed phases carry checkpoint SHAs; archives stay append-only — verbatim, never rewritten.
  • •
    Strict Human & Content Gates: Audited RED-first test requirements, per-file-class content gates. CI fails automatically with exit code 1 if documentation drifts.

Engineered for Precision

          
The 4 Core Pillars

          

            Stepwell is designed around fundamental constraints to guarantee safety, zero lock-in, and lightning-fast agent turns.
          

        


        

          
          

            

              

                🛡️
              

              
Dry-Run First

              

                All write operations generate exact line diffs first (`dryRun: true` by default). Writes happen only with explicit `--apply` — and the result is freshly re-parsed and verified before success is reported.

                ⚡
              

              
Token Economy

              

                `nextStepScope` merges step, goal, and backlog item into a single call. SHA-256 hash short-circuits prevent redundant document reads; compact JSON and `fields[]` projection keep every payload lean.
              

            

            

              nextStepScope · hashes · fields[]
            

          


          
          

            

              

                📂
              

              
Zero-Dependency Core

              

                Markdown is the only source of truth. The core engine has 0 runtime dependencies, runs natively in Node.js 22+ (type stripping, no build step), and keeps all history append-only in Git — git-blind by design.

Auditable Governance

              

                Content-risk matrix (Low, Med, High) gates every file class. Test-first (RED → GREEN) enforcement, coverage gate, and checkpoint SHAs — phases move into the archive only verified.

Structure & Schema

        
The 4-File Architecture (+ Archive Shards)

        

          Stepwell standardizes project management into four deterministic Markdown files. Once archives grow, completed history shards into per-phase files — rotation is a tool operation, never a hand edit.
        

      


      

        
        

          

            BACKLOG.md
            Active
          

          

            Priority-sorted open items (🔴 Critical → 🔵 Test gaps), one item = one block with Location/Acceptance bullets. `> No open items.` placeholders keep empty sections honest — `docs_validate` flags lying markers.
          

          

            ### [ ] H9 — Mechanical repair path *(🟢 Low)*

            - **Location:** packages/core/src/validate.ts

            - **Acceptance:** RED→GRÜN, docs_validate clean
          

        


        
        

          

            PROGRESS.md
            Active
          

          

            The permanent step index (`⬜ 🔄 ✅ ⛔`) plus detail blocks with goal, scope & acceptance — only for currently active phases.
          

          

            | Step | Task | Status |

            | 32.5 | PLAN_WITHOUT_WIP fix | ✅ |

            | 33.1 | Field test round 1 | 🔄 |
          

        


        
        

          

            docs/archive/BACKLOG_ARCHIVE.md
            Append-Only
          

          

            Completed items move verbatim with `[x]` and a done line — plus phase shards: while phase n runs, appends land in `BACKLOG_ARCHIVE.p<n>.md` (with the Done-Index line living where the block lives). The canonical file keeps the legacy stock and appends made outside a running phase.
          

          

            ### [x] H9 — Mechanical repair path *(🟢 Low)*

            - **Done:** Commit 4b6c2a1

            # shard: docs/archive/BACKLOG_ARCHIVE.p33.md
          

        


        
        

          

            docs/archive/PROGRESS_ARCHIVE.md
            Append-Only
          

          

            Completed phase blocks append verbatim, chronologically by completion time — phase numbers may stay non-monotonic (M10). With sharding, each completed phase gets its own `PROGRESS_ARCHIVE.p<n>.md` with a greppable header line; the progress table remains the permanent index.
          

          

            ### Phase 33 — Field Test (Completed: 2026-11-12T21:30)

            **Verification:** Checkpoint 4b6c2a1 (suite green)
          

        

      

    


    
    

      

        

          
Git Satellite · CLI-First

          
Parallel Phases Without Merge Hell

          

            One phase per git worktree + branch, merged back to trunk per step. The core engine stays git-blind — all git intelligence lives in the stepwell-git satellite, offered CLI-first (no MCP registration needed) and MCP-optional (`workstream_sync`).
          

        


        
        

          

            

              
              
              
              per-step workstream ritual
            

          

          

            
$ stepwell sync pull --root <worktree> # trunk → branch, conflicts abort cleanly

            
# … implement test-first, verify (typecheck + tests) …

            
$ stepwell progress-update … --apply --commit # doc commit: ONLY the doc files

            
$ stepwell sync push --root <worktree> # branch → trunk, atomic --ff-only

            
$ stepwell sync status --root <worktree> # liveness + overlap of all workstreams

          

        


        
        

          

            
🔭

            
Foresight Before Edits

            

              `predictedOverlap[]` lists files that OPEN items on both sides name in their Location bullets — visible before anyone edits them. `idCollisions[]` catches both sides reaching for the same next item ID.
            

          

          

            
🛡️

            
Guarded Operations

            

              Stable error codes — `DIRTY_TREE`, `STALE_BRANCH`, `TRUNK_DIRTY`, `MERGE_CONFLICT` (clean abort with a structured report). Dry-runs share the exact guard chain of the real operation; push is atomic `--ff-only`.
            

          

          

            
📄

            
Doc-Commits Only

            

              `commit: true` on `progress_update` / `archive_item` stages only the doc files (+ archive shards) — deterministic staging, no secret risk. Code commits stay with the agent; a failed doc commit never rolls back the edits.
